# 日本語の読者向け長文 — 執筆と推敲

## Critical: 3 つの層は、上から下が見えない

「文が固い」「読みにくい」という指摘は、**別々の 3 つの問題**を指している。
**上の層のレビューを何度回しても、下の層は絶対に出てこない。**

| 層 | 症状 | 検出方法 |
|---|---|---|
| **構成** | 何が言いたいか分からない | 内容レビューで出る → `references/structure.md` |
| **温度** | 書き手がどこにもいない・冷たい | 内容レビューでは出ない → `references/prose-tics.md` F1 |
| **手触り** | 一文一文が平板・淡白 | どちらでも出ない。**実測しないと見えない** → `scripts/prose_check.py` |

まず「どの層の話か」を切り分ける。切り分けずに手を動かすと、的外れな修正になる。

## Critical: 修正後に必ず再実測する

**手触りを直す作業は、癖を増やす方向に働く。**

実際の事故: 淡白さを直すために接続詞とダッシュと言い回しを足した結果、
同じ原稿で過去に潰した癖が復活した（`——` 0→18 個、ぼかし 3→11 個、「ところが」5→25 個）。

事前診断だけでは足りない。**修正後に `prose_check.py` を再実行して、
新しい癖を持ち込んでいないか確かめる。**

## 診断スクリプト

```bash
python scripts/prose_check.py "path/to/draft/*.md"

# 媒体を指定（寄稿・専門誌は長い文を許容する。既定は web）
python scripts/prose_check.py "path/to/draft/*.md" --genre pro

# 内輪語を指定して検出（そのプロジェクト固有の語）
python scripts/prose_check.py "path/to/draft/*.md" --jargon 巻き取る,握る,温度感,刺さる

# 免責文など毎回同じ定型を除外
python scripts/prose_check.py "path/to/draft/*.md" --exclude "本記事は|免責"

# 該当行を全件表示 / JSON 出力
python scripts/prose_check.py "path/to/draft/*.md" --detail
python scripts/prose_check.py "path/to/draft/*.md" --json
```

標準ライブラリのみ。出力は 3 部構成。

1. **文体の骨格** — 1 文の平均字数 / 25 字以下の割合 / 平板な文末の割合 / 文頭接続詞の割合 / 本文率
2. **癖の検出** — ダッシュ・語尾のぼかし・読者代弁の枕・中身のない繋ぎ・接続詞の偏り・逐語重複・
   係り受け（「の」の連続・読点過多・冗長表現）・呼称ゆれ・内輪語ほか
3. **自動では出ない項目** — 主述・見出し・一貫性・温度・具体性（人間が読む）

**このスクリプトは合否を出さない。** 文体の数値はジャンル・書き手・媒体で変わるため、
単一の合格ラインを持たない設計にしてある。数値は次節の手順で自分の基準と比べる。

**`本文率`** は、ファイル全体のうち何割を「本文」として測ったかを示す。見出し・表・箇条書き・
コードは測定から除外されるため、30% を下回る原稿では文体指標の代表性が低い（癖の検出だけ見る）。

## 媒体で「長い文」の基準は変わる

**1 文の長さに唯一の正解はない。読者と読む場所で決まる。**

| 媒体 | `--genre` | 長文の検出 | 読点 | なぜ |
|---|---|---|---|---|
| note・ブログ・Web 記事・社内向け md | `web`（既定） | 80 字超 | 4 個以上 | 画面で拾い読みされる。1 文が長いと視線が迷子になる |
| 寄稿・専門誌・報告書・提案書 | `pro` | 120 字超 | 5 個以上 | 法令・通達を日常的に読む読者が紙で通読する。刻みすぎると寄稿としての落ち着きを失う |

**変わるのは検出のしきい値だけ。** 平均文長や 25 字以下の割合は媒体によらず同じ実測値を出すので、
`pro` の原稿を `web` の手本と並べて見比べることもできる。

### 短く刻めば良くなるわけではない

社労士会報への寄稿（69 文・平均 49.3 字）を `web` の基準で推敲した実例。
検出は 18 件から 1 件へ、平均文長は 35.8 字まで下がった。ところが読み比べると、
分割の副作用で **2 箇所の意味が変わっていた。**

- 「人手不足に悩む北海道の農業者」を 2 文に割った結果、「人手不足に悩む」の主語が
  農業者から地域へずれた
- 「補助金が得られることだけでなく」を「補助金が得られたこと以上に」に変え、
  書き手が言っていない優劣を足した（感情の創作。後述「感情を書くときの制約」に違反）

**どちらも `prose_check.py` は鳴らない。** 機械は「長い」までは正確に言えるが、
「短くした結果が良くなったか」は判定できない。専門家向けの原稿では、
分割そのものの必要性を先に疑う。

## 基準線の作り方

**合格ラインは配布しない。自分で作る。**

```bash
# お手本にしたい原稿と、いまの原稿を一緒に渡して同じ表に並べる
python scripts/prose_check.py "path/to/reference/*.md" "path/to/draft/*.md"
```

- お手本は「自分が読みやすいと思った他人の文章」でも「過去に評判の良かった自分の原稿」でもよい
- **2〜3 本測る。**1 本だけだと、その原稿の癖を基準にしてしまう
- 見るのは絶対値ではなく**差の向き**。「お手本より短文が 20 ポイント多い」なら詰まっている
- 同じジャンル・同じ媒体のものを選ぶ。提案書の基準を記事に当てても意味がない

**数値に寄せに行かない。** 指標を目標にすると、それ自体は満たしつつ別の癖が増える
（`references/prose-tics.md` F3 の事故）。差が出た箇所の本文を読んで判断する。

## ワークフロー

### A. 既にある下書きを推敲・改稿する

1. **媒体を決めて**（`--genre web` / `pro`）、**`prose_check.py` をお手本と一緒に実行**し現状を数値化する
2. **層を切り分ける**（構成／温度／手触り）。ユーザーの言葉だけで決めず、数値と合わせて判断する
3. 該当する参照ファイルを読む
   - 構成の問題 → `references/structure.md`
   - 温度の問題 → `references/prose-tics.md` の F1
   - 手触りの問題 → `references/prose-tics.md` の F2
   - 文が通っていない → `references/prose-tics.md` の G 章
   - 個別の癖 → `references/prose-tics.md` の A〜E
4. **修正する。事実・数字は変えない**
5. **`prose_check.py` を同じ組み合わせで再実行**する（Critical 参照）
6. **数値を変えていないことを機械的に照合する**（下の「事実の保全」）
7. before / after の指標を添えて報告する

### B. 新しく書く

1. **幹の一文**と**章ごとの一文**を先に固定する → `references/structure.md`
2. 書く前に `references/prose-tics.md` の A 章（AI 文の指紋）だけ読む。ここを避けるだけで初稿の質が変わる
3. 書く
4. `prose_check.py` → 修正 → 再実行

### C. 多観点レビューを設計する

`references/review-lenses.md` を読む。**表現校正の担当を置き忘れないこと**（実際に置き忘れて、
「文として成立していない箇所」を取り逃した事故がある）。**通し一貫性の担当は分割不可。**

## 他の文体スキルと併用するとき

ブランド文体スキル（`reverve-style-writer` など）と本スキルは、**一部で正反対の指示を出す。**
最も衝突するのは導入の型。

| 論点 | ブランド文体スキル | 本スキル |
|---|---|---|
| 読者への共感で入る導入（「〜ではないでしょうか」） | 推奨する場合がある | A1「読者の心を代弁する枕」として削除対象 |

**優先順位: ブランド文体の指定が明示されているときは、そちらを優先する。**
その場合、`prose_check.py` が出す `reader_proxy`（読者の心を代弁する枕）の検出は無視してよい。
文体の指定がないときは A1 を適用する。

**どちらを採るかを先に決めてから直す。** 決めずに両方を満たそうとすると、
片方を適用した瞬間にもう片方の検出が鳴り続け、修正が往復する。

## 事実の保全（数字を扱う文書では必須）

推敲で表現を変えるとき、数値まで書き換えていないかを機械的に照合する。目視では漏れる。

```bash
# 主要な数値の出現回数を、変更前（git HEAD）と現在で突き合わせる
for n in "1,234" "56.7" "0.89" "12%"; do
  a=$(git show HEAD:<file> | grep -o -F "$n" | wc -l)
  b=$(grep -o -F "$n" <file> | wc -l)
  [ "$a" = "$b" ] && echo "$n OK" || echo "$n ←差分あり 前=$a 後=$b"
done
```

```powershell
# PowerShell 版（git 管理外なら HEAD の代わりに退避コピーと比較する）
foreach ($n in "1,234","56.7","0.89","12%") {
  $a = ((git show "HEAD:<file>") | Select-String -SimpleMatch $n -AllMatches).Matches.Count
  $b = ((Get-Content "<file>")   | Select-String -SimpleMatch $n -AllMatches).Matches.Count
  if ($a -eq $b) { "$n OK" } else { "$n <-差分あり 前=$a 後=$b" }
}
```

差分が出たら、意図した追記か、事故かを必ず確認する。

## 感情を書くときの制約

書き手の内面は**他人には確認しようがない**。読者向けに感情を書き足す場合:

- **内面（感じたこと）は提案してよい**が、必ず本人に確認を出す
- **具体的な出来事（日付・回数・行動）は創作しない**。「3 回目の失敗でやり方を変えた」のような
  検証可能な事実は、作った時点で虚偽になる
- 対外公開物・商用コンテンツでは、追記した感情記述を**一覧にして本人に提示する**

## 引用と実名の扱い

対外公開物では、書き手の内面以外にも確認が要るものがある。

- **他者の文章を引く**なら、引用と分かる形（括弧・出典）にし、分量は自分の論を支える最小限に留める。
  要約であっても出典は示す
- **実在の人物・企業・取引先**を書くなら、特定できる形で出してよいか本人に確認する。
  公開情報だけで書けるなら、そちらを使う
- **利害のある主張**（自社サービス・自分の成果に有利な結論）は、立場を先に開示する。
  後出しになると、それまでの実測まで疑われる

## 情報の鮮度

数字や結論を本文に書く前に、**その主題について後から出た記録がないかを必ず確認する。**
前の結論が後発の調査で覆っていた実例がある。1 件の資料だけを根拠に外部公開物へ書かない。
